# ADR-0011: Port-80 System Socket Activation (`slipfork daemon install`), Single `<state_dir>/run` Runtime Directory, and Ephemeral-to-System Handover

- **Status:** Accepted — `0.1.0` UX ruling (`M3.28.1`, implemented in `M3.28.3`–`M3.28.9`; amends `ADR-0008` §§4–5 and `ADR-0010` §2/§4)
- **Date:** 2026-11-17

## Context

1. **Port-less `.localhost` origins require `:80`, and PID 1 `systemd` socket activation is the only legal bind path (`docs/research/tunnel-weaver-and-systemd-facts.md` §5):** On Linux (`net.ipv4.ip_unprivileged_port_start = 1024`), neither an unprivileged process nor `systemd --user` (which runs with empty `CapPrm`/`CapEff`) can `bind()` `127.0.0.1:80` or `[::1]:80`. Granting `setcap cap_net_bind_service=+ep` to `slipforkd` would keep ambient privileged port authority inside a long-lived user daemon and break on `nosuid` mounts; lowering host `net.ipv4.ip_unprivileged_port_start` globally mutates host kernel policy for every local process; and shipping manual multi-line `daemon unit | sudo tee ...` shell pipelines meant `slipforkd.socket` was left uninstalled in hands-on `0.1.0` testing, leaving `slipfork up` on an ephemeral `:40645` port while `http://demo.localhost` refused connections.
2. **`$XDG_RUNTIME_DIR/slipfork` splits CLI and system daemon onto two disjoint control sockets:** Under `ADR-0008` §4's two-branch `Layout::resolve`, an interactive PAM login shell sets `XDG_RUNTIME_DIR=/run/user/<uid>` while a system unit (`slipforkd.service`) or `sudo` invocation has no user `XDG_RUNTIME_DIR` (and `/run/user/<uid>` does not exist at boot before PAM login, breaking `ProtectSystem=strict` `ReadWritePaths=`). As a result, `slipforkd.service` bound `<state_dir>/run/daemon.sock` while a login-shell `slipfork` probed `/run/user/<uid>/slipfork/daemon.sock`, saw nothing listening, and silently auto-spawned a second `--listen 127.0.0.1:0` daemon.
3. **Boot-time service readiness and `:0` handover:** Today, `render_service_unit` (`crates/slipfork-edge/src/unit.rs:148-179` and `crates/slipfork-edge/tests/golden/slipforkd.service`) emits neither `Requires=slipforkd.socket` / `After=slipforkd.socket` nor `[Install]\nWantedBy=multi-user.target`. Because `slipforkd.socket` binds TCP (`127.0.0.1:80`, `[::1]:80`, `127.0.0.1:<forward_port>`) while `slipforkd` itself binds `<state_dir>/run/daemon.sock` (`0600`) and `<state_dir>/http-ingress.sock` (`0600`), a reboot today starts only `slipforkd.socket` and leaves `slipforkd.service` inactive until an HTTP request arrives on `:80`, causing the first post-reboot `slipfork` CLI call to auto-spawn a `:0` daemon. Conversely, if a user ran `slipfork` before `daemon install`, the auto-spawned `:0` daemon holds `daemon.sock` and `http-ingress.sock`, causing a newly started `slipforkd.service` to fail with `EdgeError::SocketInUse` unless handed over cleanly.

## Decision

1. **System Socket Activation Is the Sole Port-80 Bind Path (`slipfork daemon install`, `M3.28.6`):**
   - `slipfork daemon install [--user <ACCOUNT>] [--bin-dir <DIR>]... [--forward-port <PORT>]` (no `--force`) will be the single canonical installer for `:80` ingress and Ubuntu 24.04 AppArmor `userns` support (replacing the three-step `daemon unit | sudo tee` recipe).
   - PID 1 `systemd` binds `ListenStream=127.0.0.1:80`, `ListenStream=[::1]:80`, and `ListenStream=127.0.0.1:<forward_port>` via `/etc/systemd/system/slipforkd.socket` (`WantedBy=sockets.target`) and hands `LISTEN_FDS=3` to `/etc/systemd/system/slipforkd.service`, which runs unprivileged as `User=<account>` with an empty `CapabilityBoundingSet=`, `NoNewPrivileges=yes`, and `ProtectSystem=strict`.
   - In `M3.28.6`, `render_service_unit` (`crates/slipfork-edge/src/unit.rs`) and `crates/slipfork-edge/tests/golden/slipforkd.service` will be updated to add `Requires=slipforkd.socket` and `After=slipforkd.socket` under `[Unit]` plus `[Install]\nWantedBy=multi-user.target\n`, so `systemctl enable --now slipforkd.socket slipforkd.service` starts `slipforkd` immediately **and** on every boot before any CLI invocation, guaranteeing `<state_dir>/run/daemon.sock` is already served by the `:80` daemon.
   - Install orchestration will be a pure function taking `is_root: bool` (from identity at `main.rs`) and `explicit_user: Option<&str>`. Non-root invocations (`!is_root`) fail closed before touching `UnitInstaller`, printing `slipfork: daemon install writes /etc and enables system units; run it as root (sudo slipfork daemon install --user <account>)`. When `is_root`, `explicit_user` falls back to `UserIdentity::invoking_account()` (`crates/slipfork/src/user.rs` is the sole reader of `SUDO_USER`, under its fixed `PATH`, validating the result through `UserIdentity::lookup_account`; direct root without `--user` or `root`/`uid == 0` fails closed because PostgreSQL `initdb` and unprivileged world namespaces forbid `uid 0`).
   - `daemon install` writes `/etc/systemd/system/slipforkd.{socket,service}` and `/etc/apparmor.d/slipfork` atomically (`temp + rename` in the target directory) using the **exact** bytes of `daemon unit` (with flat repeatable `--bin-dir <DIR>` alternatives), rewriting only when bytes differ. If `<state_dir>/run/daemon.sock` is currently answered by a non-`:80` `slipforkd`, `daemon install` sends `DaemonControl::shutdown` and awaits socket release before driving narrow `trait UnitInstaller` capabilities (`read_file`, `write_file_atomic`, `daemon_reload`, `apparmor_replace`, `enable_now(&[ManagedUnit::Socket, ManagedUnit::Service])`, `restart_service`; `OsUnitInstaller` wired solely in `crates/slipfork/src/main.rs` — zero stringly command bag).

2. **One Canonical Runtime Directory (`<state_dir>/run`) & `Layout::for_account` (`M3.28.6`):**
   - Delete the `$XDG_RUNTIME_DIR/slipfork` branch from `crates/slipfork/src/layout.rs`. Add pure `Layout::for_account(&ResolvedAccount, ...)` deriving `runtime_dir` unconditionally as `<state_dir>/run` (`0700`, with `--runtime-dir <DIR>` as the sole explicit override), and define `Layout::resolve` as resolving the invoking account + calling `Layout::for_account` so normal CLI runs and `daemon install --user <account>` share one layout derivation. (`XDG_RUNTIME_DIR` remains read at `slipforkd`'s Composition Root solely for upstream `tpmd` `KeyStorePaths`, `ADR-0008` §1.)
   - `<state_dir>/run` lives on persistent disk alongside `<state_dir>/http-ingress.sock` and `<state_dir>/ctl/` (strictly outside `<state_dir>/worlds/` and `<state_dir>/snapshots/`, `ADR-0010` §2), exists at boot prior to PAM session creation, and fits well within Linux's 108-byte `sun_path` limit.

3. **Zero Silent Ephemeral Ports & Pre-Daemon `IngressProbe` (`M3.28.3`, `M3.28.6`–`M3.28.9`):**
   - Rootless auto-spawn (`slipforkd --listen 127.0.0.1:0`) remains the unprivileged zero-setup path for CI and containers without `systemd`, but is **never silent**: `DaemonStatus` carries `ingress: IngressInfo { addrs, port }` (`port` validated present in `addrs`), and whenever `ingress.port != 80`, `status`, `up`, `fork`, `restart`, `list`, and `open` emit the single stderr notice specified normatively in `docs/design/dx-0.1.0-ux.md` §2 rule 4.
   - `slipfork doctor` gains an advisory `ingress` check via `trait IngressProbe` (`SystemdIngressProbe` wired solely in `crates/slipfork/src/main.rs`), reporting `:80 active`, `installed but inactive`, or `not installed` without failing `DoctorReport.ok` on unprivileged hosts.

## Consequences

- Eliminates mystery ephemeral ports on workstations and VMs, closes the `$XDG_RUNTIME_DIR` split-brain between login shells and `slipforkd.service`, preserves unprivileged `CapabilityBoundingSet=` isolation, and survives reboots and `:0 -> :80` upgrades deterministically with zero fallback shims.
