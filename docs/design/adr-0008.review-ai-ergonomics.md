# Goldfish Critique — `ai-ergonomics` lens (Round 2)

- **Targets:** `docs/design/target-dx.md`, `docs/decisions/ADR-0008-ospp-v1-websocket-tpmd-resource-strategy-and-world-ux.md`, `ARCHITECTURE.md`
- **Context read:** `plan/nodes/M2/M2.1/NODE.md`, `docs/decisions/ADR-0004-opencode-implicit-worktree-routing.md`, skills `dx-first` + `engineering-laws`
- **Persona:** an LLM coding inside `.worktrees/<fork>` with `isatty == false`, no human to ask, and a shell tool that kills anything that blocks.
- **Verdict:** **FAIL** — 1 BLOCKER, 7 MAJOR, 6 MINOR

## What already works (do not regress)

- `hook run --no-tty` and `slipfork exec` are named as the non-interactive primitives, and PTY commands fail closed naming the escape hatch (`target-dx.md:62,67`; `ADR-0008:44`).
- `auth login -` keeps `#handle=` out of `argv` and redacts it everywhere (`target-dx.md:82`; `ADR-0008:25`).
- The host-port prohibition exists in prose (`target-dx.md:47`), and `--resources local` is documented as the hermetic agent-safe mode (`target-dx.md:43`).
- `--json` schemas are concrete and `[resources]` carries `{strategy, resolved, reason}` (`target-dx.md:100`).

## BLOCKER

### B1. `slipfork exec` env injection is contradicted across docs — agents will invent `.env` hacks

`ADR-0004:15` states the **plugin** "injects resolved `snow.yml` (`modes.local`) environment variables, and wraps execution through `slipfork exec --cwd <cwd>`". `ARCHITECTURE.md:238-245` instead gives `exec_in_world` an `overlay_env: &ExecEnv` parameter (`ARCHITECTURE.md:243`), implying the CLI resolves and injects. `target-dx.md:72` shows the agent-facing form `slipfork exec --world feat-billing -- uv run pytest -k billing` with **no env statement at all**, and `target-dx.md:114` describes `exec` only as "Run command non-interactively inside world".

An LLM cannot tell whether `$DATABASE_URL`, `$API_URL`, and `secrets::*` exist after `slipfork exec`. If they do not, the agent's first failing `pytest` produces `KeyError: DATABASE_URL` and its highest-probability repair is writing a `.env` file or hardcoding `127.0.0.1:5432` — precisely the corruption `ADR-0004` exists to prevent. Two docs, two answers, and the user-facing doc is silent.

**Fix:** one sentence in `target-dx.md` §1.4 — "`slipfork exec` injects the same resolved `modes.local` env as the shell hook, so `$DATABASE_URL`/`$API_URL` are valid in-world" — and delete the duplicate injection claim from `ADR-0004:15` (or restate it as "the hook only adds `--cwd`; `exec` owns env resolution"). Pick one owner.

## MAJOR

### M1. `forward --json` and in-world `$DATABASE_URL` are two different `127.0.0.1:<port>` values with no disambiguation

`target-dx.md:75-76` prints `postgres://127.0.0.1:43182/main`; `target-dx.md:38` prints `[ready] api (127.0.0.1:8000 in world netns)`. Both look like loopback URLs; only one is valid in each context. The docs never state (a) that the `forward` URI is **host-only**, (b) that the port is **ephemeral per invocation** and must never be cached or written to config, (c) that it is *not* the in-world `$DATABASE_URL`, and (d) which env var name (`$DATABASE_URL`) the `pg_databases.main` target corresponds to. The `--json` object (`{id, host_addr, uri}`) carries no env-var mapping field, so an agent must guess the association.

### M2. `slipfork forward` blocks forever — an agent calling `slipfork forward --json` hangs its shell tool

`target-dx.md:75` and `ADR-0008:44` ("flushes URIs immediately") describe a foreground bridge that prints then serves. Nothing says "run it in the background", "it exits after `--json`", or "it serves until Ctrl-C". An LLM's shell tool has a timeout; the call returns a truncated/empty result and the agent retries or concludes the command is broken. Either `--json` must print and exit (with a separate `--serve`/`--follow` for the bridge) or the doc must state the backgrounding requirement explicitly.

### M3. `--json` does not guarantee a clean stdout stream — `json.loads` will break on `up --json`

`target-dx.md:98` only promises "`--json` disables spinners/ANSI", while hooks stream stdout/stderr live (`target-dx.md:51`; `ADR-0008:43`) and `[secrets]` / `[resources]` / `[hook]` / `[ready]` lines print to stdout (`target-dx.md:34-39`). There is no rule that, under `--json`, streamed hook output and human diagnostics move to **stderr** (or are embedded in the document). Any agent doing `json.loads(stdout)` on `up --json` gets a parse error on the first `[hook]` line — and its likely repair is to stop using `--json`.

### M4. `cwd` → world resolution has no ancestor-walk rule and no `--world` escape hatch on `up`

`target-dx.md:30` and `ADR-0008:43` define resolution as `<vcs_root>/.worktrees/<fork>` → fork, repo root → `canonical`. Agents routinely run from `/repo/.worktrees/feat-billing/api/src`. Nothing states longest-ancestor-prefix matching, nor the fail-closed behavior outside a repo. Worse, `up` is the **only** world command with no `--world <fork>` (`target-dx.md:110` vs `:111-123`), so a mis-resolved `cwd` cannot be corrected except by `cd`. The failure mode is `slipfork up` silently booting `canonical` from inside a fork's subdirectory — the exact cross-world corruption `ADR-0004:8` calls out.

### M5. Dual syntax (`--world <fork>` **and** positional `[<fork>]`) is a per-command matrix an LLM must memorize

`target-dx.md:106` codifies the flag for all world commands plus positional shorthand on `shell`, `logs`, `down`, `share` only; `fork`/`drop` are positional-only (`target-dx.md:112-113`). Two ways to name the same world violates "one canonical way" and creates a 4-of-14 asymmetry. An agent that learns `slipfork down feat-billing` will try `slipfork hook run api:pre-deploy feat-billing` and get a parse error or, worse, treat the fork as a hook ID. Delete the positional shorthand; keep `--world` only.

### M6. `--json` coverage is partial, and there is no error envelope

`down`, `hook run`, `logs`, `share`, `secret list`, and `auth login` have no `--json` (`target-dx.md:111,118-125`). `secret list --json` is the sharpest loss: an agent must verify a key exists **without echoing values** and can only scrape the human table. Separately, no doc defines what `--json` emits on failure (stderr text? `{"error": ...}` on stdout? exit code only?), so every agent must special-case failure parsing per command.

### M7. The agent's session context note is unspecified — the host-port prohibition never reaches the model

`ADR-0004:16` promises a "2-line `<context key="slipfork-world">` note", and that note is the *only* channel that reaches the model before it types a command. None of the three targets pin its content: no origin URL, no bound fork name, no "never use host `127.0.0.1:5432`/`:8000`", no "use `slipfork exec`". The prohibition lives only at `target-dx.md:47`, which the agent never reads. Implementers will ship a vague note and the guardrail evaporates. Specify the exact two lines (world name + origin + the prohibition + the `exec` pointer).

## MINOR

### m1. `auth login -` stdin hygiene unstated
`target-dx.md:82` pipes with `printf '%s\n'` (trailing newline) while `ADR-0008:25` requires `PairingUrl::parse` to fail closed on malformed input. Nothing says trailing `\n`/`\r\n` is trimmed, or that `-` with a TTY stdin fails closed instead of hanging. Agents mix `echo` and `printf` freely.

### m2. `exec --cwd` vs `--world` precedence undefined
`target-dx.md:114` allows both. If `--cwd` points into a different fork than `--world`, which wins? Unstated; the agent will assume `--world` and get the other world's filesystem.

### m3. `up` readiness is undefined
`target-dx.md:30,38` say "waits for declared component `internal_ports` readiness" — TCP accept, or first HTTP 2xx? An agent that runs `slipfork up --json` then immediately `slipfork exec -- curl` will flake against a listening-but-not-serving port.

### m4. Rescue block does not offer the hermetic retry
The rescue commands (`target-dx.md:61-65`) omit `slipfork up --resources local` / `fork --resources local`, even though `target-dx.md:43` labels that mode "safe for agent runs". Agents retrying a failed hook against shared dev state is the outcome this flag exists to prevent.

### m5. `hook run --no-tty` result contract unstated
`target-dx.md:62,119` never say whether `--no-tty` streams output live, preserves the hook's exit code, or re-runs dependent phases. An agent needs the exit code to decide "fix code" vs "fix environment".

### m6. `list --json` `state` enum unenumerated
`target-dx.md:99` shows `"state": "running"`; the human table shows `failed` (`:92`). `starting`/`stopped`/`gone` are unlisted, so agent branching on state must guess the full set.

### m7. `db`/`redis` non-TTY escape hatch has no example
`target-dx.md:120` says "use `exec` for non-TTY SQL" but never shows the one-liner (`slipfork exec --world f -- psql "$DATABASE_URL" -c '...'`). Agents copy examples, not prose.

## Fix priority

1. **B1** — decide the single owner of `exec` env resolution and state it in `target-dx.md`.
2. **M3, M4, M1** — the three that silently corrupt an agent's world (`stdout` purity, `cwd` resolution, `127.0.0.1` ambiguity).
3. **M2, M7** — hang-forever `forward` and the missing context note.
4. **M5, M6** — delete the dual syntax; complete or explicitly scope `--json`.
5. MINORs are one-line doc additions; batch them into the same sweep.
