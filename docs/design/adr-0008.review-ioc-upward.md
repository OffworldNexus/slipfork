## 1. BLOCKER

### `IOC-BLOCK-1` — World lifecycle is split across two processes with no port that can carry it

The DI tree assigns `WorldSpec` materialization to the CLI process and `WorldHandle` ownership to the daemon process, but the only crossing type is a 4-method control socket.

**Contradictory statements**

1. `WorldHandle` is opaque and **engine-scoped**: `pub struct WorldHandle(/* private engine-scoped token */)` (`ARCHITECTURE.md:217`), minted by `clone_world(&self, spec: &WorldSpec) -> Result<WorldHandle, EngineError>` (`ARCHITECTURE.md:234`).
2. `slipforkd` must use that handle to proxy traffic: "proxies `shared_hosts` via `WorldEngine::dial_world_tcp`" (`ARCHITECTURE.md:89`), `dial_world_tcp(&self, world: &WorldHandle, port: u16)` (`ARCHITECTURE.md:254`), `ADR-0005…:34`.
3. The daemon must also **destroy** it: "`DaemonControl::share_world(&project, &target)` tears down the running `WorldHandle`" (`ADR-0005…:39`).
4. The CLI owns the only materializer: "owns `WorldSpec` materialization; holds NO `TunnelLease`" (`ARCHITECTURE.md:23`), "single `WorldSpec` materializer" (`ARCHITECTURE.md:92`), "CLI orchestrator owns the single `WorldSpec` materializer" (`ARCHITECTURE.md:320`).
5. The crossing port cannot carry it: `DaemonControl` exposes only `register_world`/`release_world`/`share_world`/`unshare_world` over `0600` Unix JSON-line IPC (`ARCHITECTURE.md:29`, `ARCHITECTURE.md:321–326`). There is no `materialize`, `exec`, `exec_interactive`, `logs`, or `dial` method.

**Why this cannot be papered over**

- An engine-scoped token minted by the CLI's engine instance is meaningless to the daemon's engine instance, so `dial_world_tcp` on a CLI-minted handle either fails or silently resolves the wrong world.
- The alternative — send `WorldSpec` over IPC — puts `ExecEnv` on the wire, and `ExecEnv` deliberately exposes plaintext only at `Command::env` with a redacting `Debug` (`ARCHITECTURE.md:203–207`). Serializing it would leak every secret value into the control socket and into any log of that socket.
- `InteractiveTty<'a>` "borrows TTY fds + initial window size" and is "wired at the Composition Root" (`ARCHITECTURE.md:225–227`). `slipfork shell`, `db`, `redis`, and `hook run` construct it in the **CLI** process (`ADR-0008…:44`), so a daemon-owned engine can never be handed it.
- `docs/design/target-dx.md:26` makes `slipforkd` mandatory for `slipfork up`, so "the CLI also holds an engine" is not a legitimate reading: two engines then exist and only one can own the netns/instance.

**No escalation exists.** `plan/HUMAN.md` contains no `direction-challenge` for world-handle ownership (`H-001`…`H-009` are all closed/answered or about `incusd`/`weaved`), so this is currently papered over, contrary to `NODE.md` §12 and `ARCHITECTURE.md:5`.

**Required resolution (pick one, then amend `ARCHITECTURE.md` §1/§3.3/§3.4 + `ADR-0005` §2)**

- **Option A (recommended):** `WorldHandle` becomes a host-global `WorldId` (netns name / Incus instance name), the **daemon** owns the only `WorldEngine`, and `DaemonControl` grows `materialize(&WorldSpecWire)`, `exec`, `exec_interactive` (TTY fds passed via `SCM_RIGHTS` or a per-invocation `slipforkd`-spawned PTY), `logs`, and `dial`. `WorldSpecWire` carries secret **references**, resolved daemon-side through the injected `SecretProvider`.
- **Option B:** the CLI keeps the engine and `slipforkd` becomes a pure TCP proxy: `register_world(project, target, host_loopback_port)` and no `WorldEngine` in `slipfork-edge`. Trade-off: the CLI must keep a bridge alive per world, so `up` cannot exit — a DX regression against `target-dx.md:26`.
- Either way: file `plan.py human add --kind direction-challenge` **before** `M2.6`/`M2.8` land, because both nodes implement opposite sides of this.

## 2. MAJOR

### `IOC-M1` — `[resources]` policy has no single owner; `slipfork-ospp` depends on `slipfork-dag` for two enums

- `ResourceMode`/`ResourceStrategy` live in `slipfork-dag` (`ARCHITECTURE.md:127–141`, `ADR-0008…:33–38`), `DumpPolicy` lives in `slipfork-ospp` (`ARCHITECTURE.md:167–172`), and the precedence ladder `Skip > Refresh > ResourceStrategy` (`ADR-0008…:38`) spans both crates. No function owns it, so `slipfork up`, `slipfork test` (`TestCoordinator`), and `slipfork-ospp` will each re-derive it — the parallel-pipeline smell.
- The net client therefore depends on the config/DAG crate: "`crates/slipfork-ospp` … depends on `slipfork-world`, `slipfork-snow`, `slipfork-dag`" (`ARCHITECTURE.md:87`). A WebSocket client should not need the DAG planner to know a strategy enum.
- Ownership of the `snow.yml` ID cross-check is stated twice, differently: "the Composition Root cross-checks declared IDs … via `ResourcesSpec::validate_declared_ids`" (`ADR-0008…:35`) versus "Only the Composition Root / `slipfork-ospp` combines `SnowFile` + `ResourcesSpec`" (`ARCHITECTURE.md:122`).

**Fix:** move `ResourceMode`/`ResourceStrategy`/`DumpPolicy` into `slipfork-world` (pure serde enums, zero new deps); keep `ResourcesSpec` parsing in `slipfork-dag`; add one resolver `ResourcePlan::resolve(mode, policy, offer: Option<&RemoteResourceOffer>) -> ResourcePlan` in `slipfork-ospp`; make the `[resources]` diagnostic lines and the `--json.resources` array (`target-dx.md:35–36,100`) render that single `ResourcePlan`. Then `slipfork-ospp` depends on `slipfork-world` + `slipfork-snow` only, and the CR is the sole ID cross-checker.

### `IOC-M2` — `slipforkd` cannot route `*.localhost` without the manifest's `domains[]`, and no port carries them

- The mandated parser needs the domain set: `LocalHostRoute::parse(project, snow_domains: &[&str], host_header)` (`ADR-0005…:27`), and `WorldTarget::validate(&self, snow_domains: &[&str])` in the shipped crate (`crates/slipfork-world/src/lib.rs:109`).
- The daemon is the router (`ARCHITECTURE.md:89`, `ADR-0005…:27–37`) but is registered with `register_world(&self, project: &ProjectSlug, target: &WorldTarget)` only (`ARCHITECTURE.md:322`) — no domains, no `snow.yml`, and `slipfork-edge` is not declared to depend on `slipfork-snow` (`ARCHITECTURE.md:89`).
- Consequence: `slipforkd` must either read `snow.yml` itself (a second config root, violating the two-entrypoint rule at `ARCHITECTURE.md:11–14`) or re-implement host parsing (a parallel pipeline beside `LocalHostRoute`).

**Fix:** carry routing config into the daemon once — `register_world(&self, project, target, snow_domains: &[&str])` or an explicit `ProjectRouting { project, snow_domains }` registration — and state normatively that `slipforkd` never reads `snow.yml`/`slipfork.toml`.

### `IOC-M3` — `EngineCapabilities` is a 4-boolean bag carried into the M2 trait with no named consumer

- `fn capabilities(&self) -> EngineCapabilities` survives into the M2 trait (`ARCHITECTURE.md:231`) but `EngineCapabilities` is **never defined** in `ARCHITECTURE.md`.
- In code it is exactly the banned shape: `disk_cow`, `stateful_ram_snapshot`, `isolated_netns`, `uid_passthrough` (`crates/slipfork-engine/src/lib.rs:27–33`). Nothing states who consumes it, so call sites will drift into `if caps.stateful_ram_snapshot { … } else { … }` — `match kind` sprawl wearing a struct.
- Meanwhile `ARCHITECTURE.md:259` already forbids the adjacent smell ("Neither `slipforkd` nor `slipfork forward` inspects `engine.name()`") without extending the rule to `capabilities()`.

**Fix:** either (a) delete `capabilities()` from the M2 trait and let `SnapshotMode::StatefulRam` fail closed with a typed `EngineError` (the conformance suite is the honest capability statement), or (b) keep it, define it in `ARCHITECTURE.md` §3.3, name the **single** consumer (the `WorldSpec` materializer choosing `SnapshotMode`), and state that no other call site may branch on it.

### `IOC-M4` — "Single `WorldSpec` materializer" has no port, so M3 must build a second one

- The invariant is asserted three times (`ARCHITECTURE.md:23`, `:92`, `:320`) but no type or trait implements it; `WorldSpec` is a plain struct in `slipfork-engine` (`ARCHITECTURE.md:209–214`).
- M3 needs to materialize worlds too: `TestCoordinator` → `DaemonControl` (`ARCHITECTURE.md:71`), pre-warmed `TestSlot` pool owned by `crates/slipfork-test` (`ARCHITECTURE.md:91`), slot-stable `WorldSpec.base_env` applied at pre-warm (`ADR-0006…:49`), and `WorldSlotContext` handed to adapters (`ARCHITECTURE.md:422–427`). `crates/slipfork-test` cannot call a CLI-private function, so it will grow its own materializer.

**Fix:** declare `trait WorldMaterializer { fn materialize(&self, request: &WorldRequest) -> Result<WorldHandle, EngineError>; }` in `slipfork-engine`, implement it **once** in `crates/slipfork` (the Composition Root), and inject it into both the CLI and `TestCoordinator`. Then the "single materializer" claim becomes mechanical instead of aspirational.

### `IOC-M5` — `FallbackDeviceKeySigner` hardcodes two concrete signers, unlike its own sibling composite

- `FallbackDeviceKeySigner { primary: TpmdDeviceKeySigner, fallback: SoftwareP256Signer }` (`ADR-0008…:19`, `ARCHITECTURE.md:44`) names concrete adapters, while the analogous secret composite is generic: `LayeredSecretProvider<Primary, Fallback>` (`ARCHITECTURE.md:113–116`).
- Consequences: the shared `DeviceKeySigner` conformance suite cannot drive the fallback predicate with a fake primary (`Unavailable` / `BelowFloor` / `StoreClosed` / malformed frame, `ADR-0008…:19`) without a live `tpmd`; and a third signer (`keyring`, hardware-token) cannot be inserted without editing the composite.

**Fix:** `FallbackDeviceKeySigner<P: DeviceKeySigner, F: DeviceKeySigner>` mirroring `LayeredSecretProvider`, with the predicate (`fallback only on absent/Unavailable`) implemented once and proven by a conformance case per branch.

## 4. Upward direction verdict

The M2 tree is **one decision away** from clean. Everything except the world-lifecycle split fits a single synchronous trait tree: `WorldEngine`, `SecretProvider`, `DeviceKeySigner`, `SeedDumpStore`, `TunnelRegistrar`, `VcsWorkspaceFactory`, `TestAdapter` are all capability-honest ports with no downcasts, no extras bags, and no unisolated fallbacks.

`IOC-BLOCK-1` is not a documentation nit — it decides whether `slipforkd` embeds the engine (Option A) or proxies a CLI-held bridge (Option B), and `M2.6`/`M2.8` cannot both be implemented before that choice is recorded. Per `NODE.md` §12 and `ARCHITECTURE.md:5`, this must be escalated as a `direction-challenge` rather than resolved by whichever node lands first.

`IOC-M1`…`IOC-M5` are all one-owner/one-type fixes; none requires a new crate or a new dependency beyond what `ADR-0008…:55` already lists.
