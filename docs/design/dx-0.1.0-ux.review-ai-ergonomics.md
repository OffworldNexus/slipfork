# Review: ai-ergonomics lens

Reviewed: `docs/design/dx-0.1.0-ux.md` (M3.28.1, revision `eb15d1f`), against `target-dx.md`, `ADR-0011`, `ARCHITECTURE.md` §1–§3, and the real consumer `packages/opencode-slipfork/src/cli.ts`.

## Findings

[BLOCKER] §3/§10 — `--json` has no single envelope: `status`/`open`/`drop`/`down`/`secret`/`daemon install` emit `{"ok": true, ...}`, `up`/`restart`/`fork`/`ps`/`prune`/`daemon unit`/`forward` emit no `ok`, `list`/`support` are bare arrays, `snow resolve` is a bare map, and `doctor`/`exec`/`shell`/`db`/`redis` reuse `ok` for probe-health/exit-status -> one rule: every success is `{"ok": true, ...}` (arrays under `"worlds"`/`"integrations"`, vars under `"vars"`), and the probe/exit booleans become `healthy`/`success` so `ok` only ever means "the command ran".
[BLOCKER] §10 `exec`/`shell`/`db`/`redis` — `--json` is child stdout passthrough *followed by* a JSON object, so `JSON.parse(stdout)` is impossible and the plugin's only shell path (`buildExecCommandLine`) becomes undecodable -> these four passthrough verbs reject `--json` with one actionable line (`slipfork: exec passes child stdout through; use the exit code`) and keep any trailer object on stderr.
[MAJOR] §10 `up`/`restart`/`fork` — the payload carries no `ingress`, no `parent`, and no `services[]`, so an agent that only ever runs `up` cannot learn the ingress port (reproducing complaint #9, and under `--json` §2 rule 4 suppresses the `:40645` notice entirely) without a second `status` call -> return `status`'s per-world object (`world`,`parent`,`state`,`origin`,`worktree`,`lineage`,`services[]`) plus `changed`/`restarted`/`resources`, with top-level `ingress {addrs, port}`.
[MAJOR] §3/§8.2 — `WorldLineage` is specified only by a fully populated example, so `rootfs`/`base`/`seed`/`millis`/`digest`/`rebuilt` never appear as `null` and an agent cannot type the payload -> add a normative schema block stating every optional field is `null` (never omitted) and that `lineage.rootfs.cache` is `hit|miss` while `lineage.services[].cache` is `hit|miss|miss_offline`.
[MAJOR] §3/§8.2 — `id` names an OCI image in `lineage.services[]` (`postgres:18`) but a service instance in `services[]` (`pg_clusters.psql`), so a join on `id` silently returns nothing -> rename the lineage key to `image`.
[MAJOR] §3/§10 — the error envelope is `{"ok": false, "error": "<prose>"}` with no stable `code`, no `next`, no stated exit code, and no statement that it lands on stdout -> emit `{"ok": false, "code": "<stable snake_case>", "error": "<one line>", "next": "<exact command>"}` on stdout with exit 1 (2 for usage).
[MAJOR] §5 — `ps` fails closed for a *known but stopped* world, so the natural read-only probe returns non-zero and "unknown world" and "not booted" share one message -> return `{"ok": true, "world": str, "state": "stopped", "services": []}` with exit 0 for a known-stopped world, failing only for an unknown one.
[MAJOR] §10/§4 — `up --json` pins `"state": "running"`, so a failed boot has no representable payload and an agent cannot distinguish "world exists in `failed`, inspect it" from "nothing happened" -> on boot failure emit `{"ok": false, "code": "boot_failed", "world": str, "state": "failed", "log": str, "next": "slipfork logs --world <W>"}` with exit 1.
[MAJOR] §10 — `restarted: [str]` is undefined (bare ids, no `kind`, no stated `[]`-vs-`null` on the unchanged path), so an agent cannot match entries to `services[]` -> `restarted: [{"id": str, "kind": "component"|"backing_service"}]`, always `[]` when nothing restarted.
[MAJOR] §10/§2 rule 4 — `--json` position is contradictory: the table writes `slipfork up --json` while the shipped plugin builds `slipfork --json fork`, and nothing says the flag is accepted on both sides of the subcommand -> declare `--json`/`-v`/`--state-dir`/`--runtime-dir` `clap` `global = true` and pin both positions in `critical_cli`.
[MAJOR] §1.1/§2/§5 — read verbs auto-spawn `slipforkd` (bare `slipfork`, and `status`/`list` emit the ingress notice), so an agent probing "is a daemon up?" creates one with a new `pid` and a fresh ephemeral port, and §10 never states this -> add an `auto-spawns?` column to §10 and make `status`/`list`/`ps` side-effect-free (`{"ok": true, "daemon": null, "worlds": []}` when nothing is listening).
[MINOR] §4 — `[restarted] pg_clusters.psql, api` is bracketed internal jargon on the happy path (the same class as evidence #8's `[resources]`) and duplicates `(running, changed)` -> delete the line; `changed: true` already carries it.
[MINOR] §3 — "24 subcommands + `help` = 25 entries" disagrees with §10 (23 `clap` variants / 24 rows), so neither an agent nor `check_docs_honesty.py` has a normative enumeration -> state the exact variant list and have the checker assert the set, not a count.
[MINOR] §3/§10 — `state` denotes two domains (`running|failed|stopped` for worlds, `running|exited|stopped` for services) and `exited` vs `stopped` is never defined -> rename the service key `service_state` and define both enums in one table.
[MINOR] §10 `snow resolve` — the literal `[REDACTED]` is indistinguishable from a real secret value, and a bare map collides with the envelope if a project declares `secrets::ok` -> `{"ok": true, "vars": {"<KEY>": {"value": null, "secret": true}}}`.
[MINOR] §6 — `open --json` on a headless host is undefined (error or success), so an agent loses the `origin` it already has -> `{"ok": false, "code": "no_browser", "origin": str, "next": "slipfork open --remote"}` with exit 1.
[MINOR] §10 `drop`/`down` — `dropped: false` / `released: false` have no stated exit code, so idempotent re-runs are indistinguishable from failures -> state both are exit 0.
[MINOR] §1/§8.2 — `-v` and `--json` are presented as alternatives for the same lineage detail -> state `--json` is always maximal and `-v` only changes human rendering.
[MINOR] §1.6/§10 `list` — `list` returns absolute `worktree` paths but `--world` rejects them and there is no global `--repo`, so an orchestrator managing two projects must `cd` between calls -> accept an absolute worktree path as `--world` (or add global `--repo <DIR>`).
[MINOR] §3/§5 — `status` (fleet + per-world `services[]`) and `ps` (one world + `services[]`) are two ways to answer "what is running in my world" -> state `ps` is the canonical per-world process view and `status` is the fleet view, so agents do not alternate.
[MINOR] §10 `logs` — `--json` is NDJSON while every other verb is one document, and each line carries no `world`, so multiplexed attribution needs a second filter -> document `logs --json` as the single NDJSON exception (exempt from the one-document rule) and add `world` to each line.

## Needs human decision

- `restart` on a stopped world: keep fail-closed (human-safe: never silently boot a world you thought was running) or boot it with `changed: true` (agent-safe: one verb for "make it fresh")? Today's spec picks fail-closed but automation must branch on `status` first.

## Author disposition (`M3.28.2`)

- **Applied in place:** both BLOCKERs (one `--json` rule set with a named, closed collection exception; `exec`/`shell`/`db`/`redis` reject `--json`), and 8 of 9 MAJORs — `parent` + `ingress` on `up`/`restart`/`fork`, normative `WorldLineage` typing with explicit `null`s, `image` vs `id` split, error envelope `{"ok": false, "code", "error", "next"}` on stdout with exit `1`/`2`, `ps` read-only for known worlds, representable `boot_failed`, defined `restarted: [str]`, global-flag position pinned.
- **Resolved as documented, not changed:** auto-spawn on read verbs stays (bare `slipfork` = status must work on a fresh host); `§1` now states it, and `status` reports the resulting `pid`/`ingress`, so "did I just create a daemon?" is answerable. Making reads fail-closed is a product decision, not a wording fix.
- **Applied from the MINORs:** unbracketed `restarted`, `23` subcommands + `help`, both state enums defined, `null` (not `[REDACTED]`) for redacted vars, headless `open` as `no_browser`, `drop`/`down` exit `0`, `--json` maximal / `-v` human-only, `--world` selector grammar documented, `status` vs `ps` roles stated, `logs` NDJSON exception documented (no per-line `world`: `logs` is single-world).
- **Needs-human-decision item:** kept fail-closed. `restart` on a `stopped`/never-booted world still refuses with one line naming `slipfork up`, because silently booting a world the caller believed was running is the failure the owner hit (#12). Recorded here for a later product call; not a `0.1.0` blocker.

- **Round 3 (reviewer gate):** rulings R1–R14 applied — the payload gaps this lens raised are closed by `services[]` + `next` on `up`/`restart`/`fork`, `state` on `ps` (one read), a single failure document with per-code extras, and per-verb documents instead of a shared envelope.

VERDICT: changes-applied
