## MAJOR findings

### `C-M1` — The dead M1 REST type has a deletion directive but no owning task

- **Evidence:**
  - The directive exists: `ADR-0008:55` ("`M2.4` deletes `OsppBundle` and `MemorySecretProvider::from_bundle`"), `ARCHITECTURE.md:85`, `ARCHITECTURE.md:119`.
  - The owner does not carry it: `plan/nodes/M2/M2.4/NODE.md` Goal, Design/Invariants 1–5, and Acceptance never mention `OsppBundle` or `from_bundle`.
  - `rg -n 'OsppBundle|from_bundle' plan/` returns **zero** matches across the whole plan tree.
  - The type is still live and publicly exported: `crates/slipfork-snow/src/provider.rs:143` (`pub struct OsppBundle`), `:160` (`from_bundle`), `crates/slipfork-snow/src/lib.rs:20` (pub re-export).
  - `ADR-0001:23` compounds the ownership error by saying the type is "deleted outright in `M2.1`/`M2.4`", although M2.1's write lock excludes `crates/**` and its Acceptance is doc-only (`plan/nodes/M2/M2.1/NODE.md:9,42-67`).
- **Why this is MAJOR:** "Incomplete cleanup of scrapped ideas" is a named cruft smell. The ADR now *orders* the deletion, but the node that will execute it does not know about it, so the M1 REST struct survives M2 by default. A normative deletion clause with no executable owner is indistinguishable from no clause at all.
- **Required fix (in scope):** `ADR-0001:23` must name **only** `M2.4` (M2.1 deletes no code).
- **Required escalation (outside M2.1's lock):** amend `plan/nodes/M2/M2.4/NODE.md` with an explicit invariant + acceptance line (`! rg -q 'OsppBundle|from_bundle' crates/slipfork-snow/src`). If unamended, this becomes a BLOCKER at the M2.4 gate.

### `C-M2` — The "Complete" CLI table omits the shipped `snap` command and names a command that does not exist

- **Evidence:**
  - `docs/design/target-dx.md:104` is titled "Complete M2–M3 CLI Command Table"; the table (`:110-129`) has no `snap` row.
  - `snap` ships today: `crates/slipfork/src/main.rs:62` (`Snap` variant), and it is published in `docs/reference/cli.md:36`, `docs/index.md:11,25`, `README.md:11,43`.
  - `docs/design/target-dx.md:112` says `fork` "replaces M1 PoC `world`", but no `world` subcommand exists — the M1 CLI is `Doctor | Snow | Dag | Snap | Fork | Exec | Drop` (`crates/slipfork/src/main.rs:48-95`).
  - No ADR and no M2 node states whether `snap` survives; `rg 'snap' plan/nodes/M2` returns nothing.
- **Why this is MAJOR:** The table is the single normative CLI surface for the DX spec and M2.16/M2.17. A command that is shipped, published, and unowned is exactly the "leftover terminology / scrapped idea" smell; the `world` reference is a stale name for a command that never existed.
- **Required fix:** add a `snap` row with an explicit keep-or-delete decision (if deleted, name the M2 node that deletes it and the published pages that must be swept), and replace "M1 PoC `world`" with the real M1 command names.

### `C-M3` — `logs` / `shell` / `down` / `share` are specified with two incompatible grammars

- **Evidence:**
  - `ADR-0008:33`: `slipfork logs [<fork>] [<component_or_hook>]` and `slipfork shell [<fork>]` (positional fork).
  - `ADR-0008:44`: `slipfork logs [--world <fork>] [<target>] ...` and `slipfork shell` (no positional fork).
  - `ADR-0008:56`: `slipfork share [--stop] [<fork>]`; `ADR-0005:39`: `slipfork share [--stop] [--world <fork>] [<fork>]`.
  - `docs/design/target-dx.md:106` promises a positional `[<fork>]` on `shell`, `logs`, `down`, `share`, but the table rows contradict it: `down [--world <fork>]` (`:111`) and `logs [--world <fork>] [<target>]` (`:118`) have no fork positional.
- **Consequence:** `slipfork logs feat-billing` means "fork `feat-billing`" under one reading and "target `feat-billing`" under the other. An agent cannot resolve this from the docs; the implementation will pick one and the other text becomes a permanent lie.
- **Required fix:** one grammar. `--world <fork>` is the uniform selector; a positional `[<fork>]` exists only on commands with no other positional (`shell`, `down`, `share`), while `logs` keeps `<target>` positional and drops the fork shorthand. Then make `ADR-0008:33,44,56`, `ADR-0005:39`, and `target-dx:106,111,117-118,123` agree verbatim.

### `C-M4` — Two `ResourceCoordinates` constructors, no supersession rule, no owner

- **Evidence:**
  - `ARCHITECTURE.md:85` lists `ResourceCoordinates::for_world` / `local_for_world` as the live API; `ARCHITECTURE.md:122` specifies the `for_world(...)` signature.
  - Only `local_for_world` exists: `crates/slipfork-snow/src/model.rs:620`, and its doc comment declares it "the **sole** local coordinate constructor" (`model.rs:614-616`).
  - `rg 'fn for_world' crates/` → zero; `rg 'for_world' plan/` → zero; neither `M2.4` nor `M2.5` NODE.md mentions it.
- **Why this is MAJOR:** Two public constructors for one type is dual-way API, and the design-of-record mandates a function no plan node builds. Either the M1 constructor is superseded (then it must be deleted in the same node that adds `for_world`) or `for_world` is redundant (then it must leave `ARCHITECTURE.md`). Leaving both listed is the "pick one canonical contract" violation.
- **Required fix (in scope):** choose one in `ARCHITECTURE.md:85,122` and state the deletion/supersession explicitly. **Escalation:** name the owning node, or drop `for_world` from the M2 design.
