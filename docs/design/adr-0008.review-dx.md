## 3. MAJOR

### M1 — `up` cannot target a world, but `down` can
`target-dx.md:106` promises "world-scoped commands accept `--world <fork>` uniformly"; `target-dx.md:110` lists `up` with no `--world`; `target-dx.md:111` gives `down --world <fork>`.
**Symptom:** after `slipfork down --world feat-billing` from the repo root, the only way back is `cd .worktrees/feat-billing && slipfork up`. There is no global `-C/--dir`. An agent that just stopped a world cannot restart it without changing directory, which the plugin's `--cwd` routing does not model.
**Fix:** add `--world <fork>` to `up` (and a global `-C <dir>`), or state explicitly that `up` is cwd-only and make `down` cwd-only too.

### M2 — Two addressing syntaxes for the same target
`target-dx.md:106` legalizes both `--world <fork>` and a positional `[<fork>]` on `shell`, `logs`, `down`, `share` (`:117`, `:118`, `:123`; repeated in `ADR-0005:46`). Meanwhile `fork`/`drop` are positional-only (`:112`, `:113`) and `exec`/`db`/`redis`/`forward`/`hook run` are flag-only (`:114`, `:119`–`:122`).
**Symptom:** "uniform" is false, and an LLM must memorize a per-command matrix. Every dual form doubles the chance of a plausible-but-wrong invocation (`slipfork logs feat-billing --world feat-billing`).
**Fix:** one canonical form. Recommend positional `<fork>` everywhere (matches `fork`, `drop`, `shell` in `ADR-0005:46`) and delete `--world`; or the reverse. Never both.

### M3 — `cwd` → world resolution never specifies ancestor walk
`target-dx.md:30` and `ADR-0008:43` define resolution as `<vcs_root>/.worktrees/<fork>` → fork, repo root → `canonical`. Nothing says what happens from `/repo/.worktrees/feat-billing/api` or `/repo/api`.
**Symptom:** agents run nearly every command in a subdirectory. Published plugin docs already promise the opposite of the spec's silence: `docs/agents-and-opencode.md:50` says "inside `.worktrees/<slug>` (**or any subdirectory**)". The CLI and the plugin will disagree.
**Fix:** state the rule once, normatively: nearest ancestor — inside a worktree root or any descendant → that fork; repo root or any non-worktree descendant → `canonical`; outside any repo → fail closed naming `--world`. Include symlink/`..` handling.

### M4 — `--json` has no error contract and no exit-code table
`target-dx.md:98`–`:101` define only success payloads. `prune --json` is advertised (`:116`) with no schema. `secret list`, `auth`, and `doctor` have no `--json` at all (`:124`, `:125`, `:127`).
**Symptom:** an agent gets deterministic JSON on success and prose on failure, so it must regex `error:` lines — the exact fragility `--json` exists to remove. A failing `up --json` cannot be distinguished from a failing `fork --json`.
**Fix:** one envelope on failure (stderr, exit non-zero) plus a documented exit-code table, e.g.

```json
{"ok": false, "error": {"code": "hook_failed", "message": "...", "world": "feat-billing", "hook": "api:pre-deploy", "log": "...", "resources": []}}
```

and state that `--json` implies non-interactive (never prompts, never attaches a PTY).

### M5 — `exec` contract is incomplete for the canonical agent path
`target-dx.md:72`/`:114` show `exec` but never state: exit-code propagation, stdin forwarding, stdout/stderr framing, or the environment model. `ARCHITECTURE.md:203`–`:207` says `Command::env_clear()` with a `PATH`/`TERM`/`LANG`/`HOME` allowlist — invisible in the DX spec. `ADR-0004:15` says the plugin *injects resolved `snow.yml` env vars* and then wraps in `exec`, which is either redundant or contradictory with `env_clear`. Published `docs/reference/cli.md:42`–`:43` still documents `--snow-file` and exit-code propagation, both absent from the M2 table.
**Symptom:** `export FOO=1 && slipfork exec -- printenv FOO` silently prints nothing; `echo x | slipfork exec -- cat` is undefined; `--snow-file` is either silently deleted or silently undocumented.
**Fix:** document exit-code propagation, stdin/stdout/stderr, the `ExecEnv` allowlist, how extra vars are passed (`--env K=V` or `snow.yml` only), and the explicit fate of `--snow-file` (delete + update published docs in M2.19, or keep).

### M6 — The printed origin is not dialable in two documented paths
`target-dx.md:38`–`:39` prints `[ready] api (127.0.0.1:8000 in world netns)` and `[origin] http://acme.localhost` (port 80). `ADR-0005:9`/`:27` route `*.localhost` on the **host** through `slipforkd`; nothing listens on `:80` inside the world netns, and `*.localhost` resolution inside a fresh netns is unspecified.
**Symptom:** `slipfork exec --world feat-billing -- curl "$BASE_URL"` (or an in-world Playwright run) gets `ECONNREFUSED`, while the same URL works in the host browser. Separately, `target-dx.md:23` runs `slipforkd --listen 127.0.0.1:7080`, but every origin example is portless (`:39`, `:47`, `:91`, `:99`) and no flag/env tells the CLI which daemon address to use; there is also no `daemon start|stop|status` for the no-systemd path that the doc advertises as first-class.
**Fix:** specify in-world origin reachability (in-netns `:80` listener, or a documented in-world `$BASE_URL` override), the `--listen` origin port rendering (`http://acme.localhost:7080`), and a `--daemon <addr>`/`SLIPFORK_DAEMON` discovery contract plus `daemon status`. If in-world origin cannot be made reachable without a second pipeline, this is a **`direction-challenge`**, not a doc patch.

### M7 — Destructive commands have no safety contract
`target-dx.md:113` — `drop <fork>` destroys the world and removes `.worktrees/<fork>`, with no dirty-tree check and no `--force`. `target-dx.md:95`/`:116` — `prune [--dry-run | --yes]`, with bare-`prune` behaviour undefined.
**Symptom:** `drop` can delete uncommitted agent work; bare `prune` either prompts (agent hang) or deletes (data loss) depending on the implementer's mood.
**Fix:** `drop` refuses when the worktree is dirty or the world is running unless `--force`; `prune` never prompts (bare = dry-run), never touches a world shown by `list`, and `--json` enumerates every path it would delete.

### M8 — `auth` has no `status` and no `logout`
`target-dx.md:125` ships only `auth login`; `ADR-0008:25` defines pairing but no query/revocation surface. `target-dx.md:42` makes `--refresh-dump` fail closed when offline/unpaired.
**Symptom:** when `--refresh-dump` fails, neither a human nor an agent can tell "unpaired", "offline", or "resource absent" without reading prose. There is also no way to unpair a lost laptop's device key.
**Fix:** `slipfork auth status [--json]` → `{"paired": bool, "key_id": "p256:…", "backend": "tpmd:sealed", "server": "…"}` and `slipfork auth logout` (drop the local key handle; state whether the server-side registration is revoked).
