# Slipfork: Vision

> **Fork the world in milliseconds. Never rebuild what didn't change. Never clean up a test database again.**

## Why Slipfork Exists

Modern full-stack development and autonomous AI coding hit the same wall from two directions:

1. **Integration & browser test suites are painfully slow and brittle across every language:**
   - Non-Django stacks (Flask+Alembic, FastAPI, Hono/SvelteKit, Symfony/Slim, Go, Rust) have to cobble together slow Docker `testcontainers`, random port-0 `live_server` scripts, and manual per-worker migrations — while Django (`pytest-django`) spends 80% of wall time creating `test_<db>` and running `TRUNCATE` / `serialized_rollback`.
   - Test runners end up compiling frontend bundles inside fixtures, monkey-patching `STORAGES`/`CACHES` in test settings, and colliding on background workers, Redis, and S3.
2. **Parallel AI coding agents trample each other's environments:**
   - Git worktrees (and Jujutsu workspaces) isolate source files, **not** PostgreSQL databases, Redis keys, S3 buckets, background workers, or TCP ports (`:5432`, `:8000`, `:3000`).
   - Docker Compose per worktree creates `root:root` files on bind mounts, duplicates gigabytes of layers, drifts from production `snow.yml` manifests via `.env` spaghetti, and confuses LLMs with custom wrapper invocations.

Meanwhile, Linux Btrfs subvolumes, unprivileged namespaces (`userns`/`netns`/`ipcns`/`pidns`/`mntns`), and daemonless static `crun` can **snapshot and clone entire multi-service worlds via subvolume Copy-on-Write in milliseconds** (`ADR-0010` Context §2).

Slipfork bridges that gap with a **DX-First, manifest-driven (`snow.yml`) orchestrator**.

## Core Design Principles

1. **Developer Experience First (Dream Tool Docs Before Code, Zero Black Boxes):**
   - One manifest (`snow.yml` with `modes.all` + `modes.local` + `modes.cloud` and `!!` secret generation — shipped for env/secret resolution and `components.<id>.run_command` override validation in `0.1.0`, with full mode-scoped `components.<id>` add/remove/override supervision in M2) plus optional `slipfork.toml` (`[artifacts]`, `[fixtures]` with `per_world`, typed `[test]` coverage shipped in `0.1.0`, and mode-aware `[resources]` `ResourceStrategy` in M2), governed by `ADR-0006` §1's typed-manifest law.
   - **Single-Origin Worlds (`struct WorldOrigin(LocalOrigin)`, `ADR-0005`, `ADR-0011`, shipped in `0.1.0`):** each world has one `.localhost` origin known before materialization (`slipforkd` running unprivileged via `systemd` `LISTEN_FDS` `:80` socket activation or `--listen` as sole HTTP/WS ingress, `H-008`), deterministic `<= 31`-byte Tunnel Weaver service-label truncation (`<prefix>-<hash>`), a `Dockerfile`-derived read-only `$UID:$GID` `L0` world rootfs + daemonless `crun` backing-service containers (`ADR-0009`), native `git` + Jujutsu (`jj workspace`) support, and built-in container-scoped `slipfork db`, `slipfork redis`, and `slipfork forward` bridges — starting offline on `FileVaultProvider` (`0600` local-only credentials/overrides) without requiring OSPP.
   - **First-Class Hook & Migration Failure Debugging (shipped in `0.1.0`):** hooks and migrations stream stdout/stderr live; on failure, Slipfork prints the exact command and full un-truncated output, **preserves the failed world** for inspection, and prints 1-line rescue commands (`slipfork hook run <id>` with interactive TTY `stdin`/`stdout`/`stderr` for `pdb`, `slipfork logs`, and `slipfork shell`).
   - Shared host filesystem running as the developer's exact `$UID:$GID` — zero weird root files (unified onto one Btrfs subvolume per world in M3 `BtrfsEngine`, `ADR-0010`).
   - Zero-confusion OpenCode integration: creating a worktree forks the world implicitly; standard `shell` commands route automatically by `cwd` (shipped in `0.1.0` `@slipfork/opencode`).
2. **Target M3 World-Owns-The-Stack Inversion + `STP v1` Global DAG Orchestration:**
   - In `0.2.0` (`slipfork test`), Slipfork orchestrates nodes of the global DAG over the **Slipfork Testing Protocol (`STP v1`, `ADR-0006` §3)** on an inherited shared file descriptor (`SLIPFORK_PROTOCOL_FD`, an `AF_UNIX` `socketpair`): testing frameworks expose test and **persistent setup/fixture stage nodes** (DB migrations, seed factories, S3 state) that survive the setup process as frozen **read-only Btrfs subvolume snapshots** (`ADR-0010`), composing with `[artifacts.*]` / `[fixtures.*]` DAG nodes, boot-resolved `$BASE_URL` + `$DATABASE_URL`, and **hermetic-by-default `[resources]`** (`ResourceMode::Test`, `ADR-0006` §2 / `ADR-0008` §3). Integration maturity is tracked via evidence-checked support tiers (`none`..`hardened` in `support/integrations.toml`, schema shipped in `0.1.0`, CLI & ceiling in `0.2.0`; `ADR-0007`, `H-009`).
   - Stateless build outputs (`front` bundle, static assets) hash independently from origin-independent fixture snapshots (`M2`/`M3` adds `per_world = true` boot-time seeds plus pre-warmed Btrfs world slots and shared host `BrowserContext`s over `http://test-<slot>.<project>.localhost`).
3. **`OSPP v1` End-to-End HPKE Secrets, Two-Tier Vault Boundary, Protocol-Native Coverage/`mutants` & Pure Orthogonality:**
   - Shares `snow.yml` (`0.1.0`) and pairs with CI (Kerfufoo or compatible providers) over the **Open Secret Provider Protocol (`OSPP v1`, `docs/design/ospp.md`, `ADR-0008`)**: a persistent all-JSON `ospp-v1` WebSocket protocol using ECDSA P-256 (`p256`) challenge-response auth and ALTCHA + proof-of-possession browser-fragment pairing (`<url>#handle=<handle>`) to subscribe by verbatim Git `remote` with uniform ID-only `claims` (automatically derived from keys in the project's local `0600` vault plus locally-provisioned resources/domains), deliver **RFC 9180 HPKE end-to-end encrypted** per-variable secrets (`hpke-p256`, decrypted **strictly in `slipforkd` memory** with an ephemeral per-subscription keypair and **never written to the local vault or any file on disk**), push **live `env_updated` updates** that restart affected services in place, and stream **out-of-band HPKE-encrypted** PostgreSQL seed dumps (`zstd -d | pg_restore`, zero plaintext at rest) into local `base` CoW snapshots (`--no-dump` / `--refresh-dump`). OSPP remains optional for local worlds — `FileVaultProvider` (`0600`) persists strictly local backing-service passwords, `slipfork secret` overrides, and local-mode `!!` secrets across restarts — and OSPP never supplies world origins.
   - Outbound tunnel sharing (future `M4.1`, not shipped in `0.1.0`, `ADR-0011`) remains isolated behind closed `H-006` until Tunnel Weaver (`weaved`) publishes its IPC specification, while deterministic `<= 31`-byte `WeaverServiceName` truncation ships in `slipfork-world`.
   - In `0.2.0` (`STP v1`), coverage (configured via shipped `[test]` `coverage`, `coverage_report`, `coverage_fail_under`) and mutation testing (`mutants`) are first-class concepts inside `STP v1` itself rather than hardcoded per-language Rust drivers — while Blastit, Playwright traces, and Allure stay 100% decoupled via a surviving tool-owned `SLIPFORK_OUTPUT_DIR` directory (`ADR-0006` §§3, 5).
4. **The Three Iron Laws (Enforced Mechanically & by Dedicated Reviewers):**
   - **Zero Illegal Solutions (`review-legality`):** Missing credentials, sockets, or spec inputs halt immediately in `HUMAN.md` — never faked, guessed, or monkey-patched.
   - **Strict IoC/DI & Upward Challenge (`review-ioc`):** Pure domain traits wired at a single Composition Root; any spec blind spot that breaks DI clarity triggers a human `direction-challenge` before coding.
   - **Zero Pre-`1.0` Compat Cruft (`review-cruft`):** One canonical way, zero fallback branches, immediate deletion of superseded drafts (including replacing M1's REST OSPP sketch with `OSPP v1` WebSocket cleanly).

## Editor & IDE integration — 0.5.0, not shipped

> **Future milestone (`M5` / `0.5.0`, not shipped — zero vaporware):** Nothing in this section exists in `0.1.0`. No published `docs/` page and no `README.md` claim may mention editor or IDE plugins until the first one compiles, passes protected critical tests, and ships; `docs/VISION.md` (excluded from `zensical.toml`) is the sole home for this UX intent until `M5` opens its `docs/design/dx-*.md` pass.

Developers and AI agents should be able to see running CoW worlds, inspect live per-component logs, jump into a forked worktree, query a fork's database, click a remote `.localhost` origin without hand-rolling `ssh -L`, and inspect per-world test/coverage/`mutants` runs directly inside **VS Code**, **JetBrains (IntelliJ Platform)**, and **Zed**:

1. **Why `0.5.0` waits for `0.2.0` (`STP v1`) and `M4`:**
   - IDE plugins earn their keep when they surface rich per-world state — not only running services and logs, but live test runs, protocol-native coverage, and `mutants` per world from `0.2.0`'s `STP v1` (`M3.2`). `M5` therefore depends explicitly on `0.2.0` / `M4`.
2. **One control plane, N thin adapters (`DaemonControl` + `slipfork-mcp`):**
   - Extending `@slipfork/opencode`'s precedent (`packages/opencode-slipfork/`: an editor-adjacent thin adapter over `ctx.worktree.transform` + shell/context hooks that owns zero `snow.yml` secret resolution and zero world lifecycle state), every editor talks to a **versioned, typed editor RPC** over `slipforkd`'s existing `DaemonControl` seam (`<runtime_dir>/daemon.sock`, `ARCHITECTURE.md` §1, `ADR-0008` §4) — **zero per-editor business logic, and zero shelling out to scrape CLI text for state**.
   - One **`slipfork-mcp`** server exposing MCP tools and resources (`list_worlds`, `up`, `fork`, `restart`, `logs`, `db_query`, `open_url`, `exec`) makes **Zed** and every AI coding agent (Zed agent panel, OpenCode, Claude Code, Codex) first-class *for free*, while VS Code and JetBrains layer thin native UI over the exact same protocol.
3. **Imagined deep integration per editor (captured as UX intent for the post-`0.2.0` `dx-first` pass, not a frozen spec):**
   - **VS Code:** worlds `TreeView` (state, `.localhost` origin, base key, uptime), `TaskProvider` + `TerminalProfileProvider` (`slipfork shell` as a native terminal profile), `SimpleBrowser` + **`env.asExternalUri`** so a remote world's `demo.localhost` is clickable from a laptop without hand-rolled `ssh -L`, per-component `OutputChannel` log streaming, `DebugAdapterDescriptorFactory` attaching debuggers inside the world, and `slipfork doctor` findings surfaced as Problems with `fix:` code actions.
   - **JetBrains (IntelliJ Platform):** Tool Window worlds tree, Run/Debug configurations, `ProjectOpenProcessor` to open a forked `.worktrees/<fork>` checkout, execution console per component, **HTTP Client environment injection per world** (`http-client.env.json` populated with `BASE_URL` and `DATABASE_URL` so every `.http` request targets the right fork), and the native Database tool wired directly via the world DSN.
   - **Zed:** MCP `context_servers` + tasks + DAP templates over `slipfork-mcp` — zero custom extension code, deep reach.
